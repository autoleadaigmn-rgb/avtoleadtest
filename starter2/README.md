# AutoLead Starter 2.0 — local test lab

The separately deployed Cloudflare Free test and its limitations are documented in [CLOUD-TEST.md](CLOUD-TEST.md). The published GitHub Pages demo remains separate.

This directory is independent of the published demo. It uses Cloudflare Worker code, two isolated local D1 databases, a one-line iframe widget, and fictional Bayline fixtures. The server accepts only `TEST_ONLY` and `SIMULATED` mail. No Cloudflare account or paid resource is needed locally.

Requirements: Node 22+, pnpm 11.25.0. Run `pnpm install --frozen-lockfile --ignore-scripts`, `pnpm test`, `pnpm check`, then `pnpm dev`. Open http://127.0.0.1:8787/ for the lab, http://127.0.0.1:8790/ for the cross-origin one-line installation, and http://127.0.0.1:8790/responsive for narrow widget frames. The local owner button issues a signed fictional test identity only from the loopback development server. Reloading clears the browser token.

The widget script is `<script async src="https://YOUR_APPROVED_WIDGET_HOST/loader.js" data-shop="bayline"></script>`. This is an example, not a deployed URL. A client site's CSP must allow the widget origin for scripts, styles and frames. Add its exact origin to the tenant's parent allowlist. Never place owner membership, secrets or recipient addresses in public configuration.

`pnpm snapshot -- export bayline` writes a fictional local snapshot and deletion ledger to ignored `snapshots/`. Stop the dev server first. `pnpm snapshot -- restore bayline` restores only to ignored `.local/recovery`, requires a ledger newer than the snapshot, and excludes erased requests. Do not restore an old database over newer records. The published demo and CRM are separate. To pause the local lab, set `INTAKE_ENABLED` to `false` in the local Worker config and restart. The isolated cloud test and its rollback steps are in `CLOUD-TEST.md`.

Before any real client pilot: obtain separate approval for costs and real data; configure a Google web client ID with verified owner-subject membership, monitoring, a backup policy and a production privacy review. Keep `TEST_ONLY` and `SIMULATED` until a separately reviewed real-data implementation exists. The current code cannot send email or accept arbitrary personal data.

Test owner onboarding: the Cloudflare test deployment uses a public Google Web Client ID for Google Identity Services. The owner page verifies the ID token on the Worker (Google signing key, issuer, audience and expiry) before showing the Google `sub` if the account is not yet assigned. Only the `sub` identifier should be shared with the project operator; never send the ID token, password or Client Secret. Store `OWNER_MEMBERSHIPS` as a Worker secret containing a JSON map such as `{"verified-sub":["bayline"]}`. Do not place this mapping in Git, public assets or Wrangler `vars`. A valid Google login alone does not grant access: every owner API action checks the verified `sub` against the exact shop. Browser sign-out clears the in-memory token; Google ID tokens also expire and are checked on every request.

The notification outbox records intent atomically via a database trigger. A local simulated delivery receipt prevents duplicate simulated notifications across retries. A future real email adapter needs provider idempotency/reconciliation; it is not implemented here. Runtime tests use Miniflare with D1 and a locally signed fake Google certificate, and forbid outbound network except the local certificate fixture. Hosted test results are in `CLOUD-TEST.md`; Google sign-in with a real account remains untested.
